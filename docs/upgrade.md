# Upgrades and versioning

## v0.6.0

Some configs need changes, and most deployments need a step or two before the first deploy. The groups below go from what needs action to what is new.

### Before you deploy

- **Node.js 22.** `engines` requires Node.js 22 or later for the build and the npm scripts; it was 20.
- **Set `compatibility_date = "2026-06-25"` in your `wrangler.toml`.** `wrangler.example.toml` and `wrangler.dev.toml` moved from `2024-09-23` to `2026-06-25`, but your own `wrangler.toml` (gitignored) keeps the date you copied. v0.6.0 is tested only at `2026-06-25`.
- **With the widget on, upload the new widget object before you deploy.** The widget object in R2 is now named after its content (`widget.<16 hex>.js`) and starts with a license preamble. If `vendor/webmcp/v0.1.13/webmcp.js` is missing (it is gitignored), fetch it first: `npm run update-widget -- --version=v0.1.13 --sha256=<the "sha256" field of vendor/webmcp/current.json>`. Then run `npm run upload-widget` (it now passes `--remote` to wrangler; `-- --local` writes to the local state of `wrangler.dev.toml`, which `npm run dev:worker` reads), then deploy. Until the object is in R2, the widget URL the landing page names answers 503 and `/_webmcp/health` shows `widget_asset_present: false`. The v0.5 URL, `widget.<8 hex>.js`, answers 404; its object can be deleted (see [Updating the fallback widget](#updating-the-fallback-widget)).
- **If you ran preflight before, run it again.** `CONFIG_HASH` covers the validated config with every default filled in, and this release adds and changes defaults, so the hash changes for every existing TOML. The build embeds a preflight result from before the upgrade with a "preflight result is stale" warning, and `/_webmcp/health` shows that warning until you run preflight again and redeploy. If the hostname already goes through the Worker, point preflight at a direct origin hostname with `--origin` (see [Preflight](deployment.md#preflight)).
- **Update WAF rules that match the User-Agent.** The Worker's requests to origin (executors and merge routes) send `User-Agent: cf-webmcp/<version>`; it was `cf-webmcp/1.0`. Preflight sends `cf-webmcp-preflight/<version>`; it was `cf-webmcp-preflight/1.0`. A rule that matches the old string needs the new one; the deploy-token headers are the stable thing to match.
- **Update a CSP that allowlists the bootstrap by hash.** The bootstrap's URL and SRI hash change once with this upgrade (see [Bootstrap, landing page and widget](#bootstrap-landing-page-and-widget) below). Put the new `BOOTSTRAP_SRI` from `src/generated/config.ts` into `script-src` as a quoted hash source, `'sha384-...'`. With `[features].subresource_integrity = false`, `BOOTSTRAP_SRI` is `null` and there is no hash to list.
- **The health endpoint reads `CF_WEBMCP_HEALTH_TOKEN`.** v0.5.1 did not read the secret, only `[health].token`. Now the secret, when it is set, replaces `[health].token`:
  - with `[health].public = true`, an endpoint that answered everyone now answers `401` without `Authorization: Bearer <token>`;
  - with `[health].public = false` and only the secret set, v0.5.1 answered `404`; v0.6.0 answers to the bearer token and gives `401` without it.

  The answer also has two new fields, `widget_asset_present` and `origin_trials`.
- **Custom landing templates copied from the old default.** `{{widget_block}}` now carries the pairing steps: the "Pairing required" heading, the bridge commands and the widget scripts. A template that kept its own pairing heading and CLI line renders them twice; drop them (see the `{{widget_block}}` row in [`docs/customisation.md`](customisation.md)). Also add `{{bootstrap_block}}` once, before the state script (see the default template). Without it the landing registers no tools while it shows Connected.

### Config that changes meaning or fails to build

- **`fallback_widget` now defaults to `false`.** The desktop-bridge widget is opt-in. A TOML that does not set the key loses the pairing flow: the landing shows "Not connected" to a browser without WebMCP, and the widget URL answers 404. The build prints a notice for such a TOML. To keep the widget, set `fallback_widget = true` under `[features]` and read [Known limits of the desktop bridge](deployment.md#known-limits-of-the-desktop-bridge). The default, WordPress and WooCommerce templates set it to `true` explicitly.
- **A `?` in a path glob matches exactly one character.** In `[injection].exclude_paths` and `[[forms]].paths`, v0.5.1 read `?` as a regular-expression quantifier that made the previous character optional: `/search?*` matched `/search`, `/searc` and every path that starts with `/searc`. v0.6.0 gives `?` its usual glob meaning, exactly one character (`/` included), so `/search?*` now needs at least one character after `/search`. Patterns are matched against the path only, never the query string. The build warns about every pattern that contains `?`, naming the field and the pattern; check that each one still matches the pages you mean. TOMLs copied from the v0.5.1 WordPress or WooCommerce template carry `/?rest_route=*` (WooCommerce also `/?wc-ajax=*` and `/?add-to-cart=*`). These never matched, because a path holds no query string; delete them, as the templates now do. See [Path scoping](form-injection.md#path-scoping-with-paths).
- **`[agent_skills].name` must be a slug**: lowercase letters and digits in groups joined by single hyphens, at most 64 characters, even with `agent_skills` off. `name = "My Shop"` now fails validation; write `name = "my-shop"`.
- **A `[site].name` with nothing left after slugify** (a name only in a non-Latin script, say) and no `[agent_skills].name` fails the build when a SKILL.md, the skills index or the ARD entry uses the name, instead of falling back to `site`. Set `[agent_skills].name`.
- **`[site].public_url`, `[site].domain` and `[origin].base_url` are validated.** `public_url` must be an http or https origin: scheme, host (letters, digits, dots, hyphens) and an optional port, with no path (not even a trailing `/`), query, fragment or credentials. A port in `[site].domain` must run from 1 to 65535. The origin of `base_url` must be in `allowed_origins`. The error names the field.
- **Selectors are checked against what HTMLRewriter accepts.** `[[forms]]` selectors and param selectors, and the `selector` and `strip` entries of `dom_extract`, must stay within the subset in [Selector limits](form-injection.md#selector-limits). Among what now fails the build: uppercase attribute names (`[NAME=email]`), backslash escapes, the sibling combinators `+` and `~`, unsupported pseudo-classes, a comma list in a form or param selector, and a selector over 1024 characters or 64 compounds. Before, such a selector reached HTMLRewriter at request time.
- **Route paths must not start with `//`** (a protocol-relative URL names another host), and `[paths].namespace` must not be `/` or end in `/`.
- **Tool input must be declared.** A `required` name and a `url_template` placeholder must be declared under `[tools.input_schema.properties.<name>]`. An undeclared placeholder fails the build with `undeclared input name`, naming the tool and the placeholder; an undeclared `required` name fails validation, reported by its path (`tools.<i>.input_schema.required.<j>`) and its name. Only declared properties reach an executor now, so such a `required` name would be dropped, and an undeclared placeholder used to read whatever a caller sent. A `sitemap_filter` tool without a declared `query` only warns: it lists the sitemap without filtering.
- **Enums.** v0.5.1 checked `enum` only on string properties, so an enum on an integer, number, boolean or array property was ignored and any value of the right type passed. v0.6.0 enforces `enum` on every scalar type. An enum with a value that does not fit the declared type (`type = "integer"` with `enum = ["1"]`, or with `enum = [1, "1"]`), or an enum on an array (write it on `items`, where it is enforced), now fails the build with the property's path.
- **Reserved names.** `__proto__`, `constructor` and `prototype` are refused as `input_schema` property names, in `properties` and in `required`. `scan_images_c2pa` and `inspect_image_c2pa`, which Cloudflare WebMCP Labs registers, are refused as `[[tools]]` and `[[forms]]` names: a name registered twice on one page kills the Chrome renderer (see [Cloudflare WebMCP Labs on the same zone](deployment.md#cloudflare-webmcp-labs-on-the-same-zone)).
- **Origin-trial tokens are checked.** A `[origin_trial].tokens` entry that is malformed, a third-party token, issued for another origin than the site's, expired or listed twice fails the build (see [Additions](#additions)).

### Behaviour changes

#### Discovery documents

- **ARD moved to v0.91**, following [ards-project/ard-spec](https://github.com/ards-project/ard-spec) as of commit `aa3e598bb7` (the repository has no tag for it). See [`docs/ard.md`](ard.md). These apply with `[features].ai_catalog = true`:
  - The manifest is served at `/.well-known/ard.json` and advertised with `rel="ard"` in the Link header and the link tag; `rel="ai-catalog"` is no longer emitted. The robots.txt `Agentmap:` line and the llms.txt line point at the new path.
  - It is served as `application/json; charset=utf-8` instead of `application/ai-catalog+json`, and the document no longer has a `specVersion` member.
  - `/.well-known/ai-catalog.json` now answers with a 301 to `/.well-known/ard.json` (`[ai_catalog].aliases`, default `["/.well-known/ai-catalog.json"]`; set `aliases = []` to leave it to origin). The aliases take part in the build's path-collision check.
  - A config that sets `[ai_catalog].path = "/.well-known/ai-catalog.json"` keeps serving there, and the build warns: consumers of ARD v0.91 MUST fetch `/.well-known/ard.json`. Remove the line or move `path` to the default. A different custom path also warns while `/.well-known/ard.json` is not one of the aliases.
  - The entry identifier changes for some sites. The skill name in it is now built the same way as for the SKILL.md, so accents are removed (`Café` was `caf`, now `cafe`) and some letters are transliterated (`ß` becomes `ss`). The publisher segment is `[site].domain`, lowercased and without its port.
  - Unless `[ai_catalog].host_identifier` overrides it, `host.identifier` is now `did:web:` plus the host of `[site].public_url` when that is set, with a port written as `%3A`; before, it always used `[site].domain`.
  - The entry's `displayName` is now always `[site].name`, also when `[agent_skills].name` is set.
  - Merge mode: an origin document that fails the structural check is now relayed unchanged instead of being replaced by the generated one. Any `application/<x>+json` type is merged (v0.5.1 took `application/json`, `application/ai-catalog+json` and a `200` without a `Content-Type` only). When origin answers 404 at `ard.json`, its `/.well-known/ai-catalog.json` is merged instead. When origin already lists an entry with our identifier or our url, origin's entry is kept and ours is not added; v0.5.1 replaced an origin entry with our identifier by ours, and added ours next to one that only had our url. Origin documents over 1 MiB are relayed, not merged, and the generated document that stands in for a failed origin is cached for 60 seconds only.
  - Preflight probes the ARD manifest path and its aliases, and in `merge` mode also `/.well-known/ai-catalog.json`; v0.5.1 preflight probed no ARD path.
  - With `[features].agent_skills` on as well, the build warns when `[site].domain` is not a fully qualified domain name (localhost, an IP address, a single label). With the feature on, in any mode, a `[site].domain` the URL parser refuses as a host (an invalid IPv4 address such as `1.2.3.4.5`) fails the build with a named error.
  - The build writes the generated document to `src/generated/ard.json`; it was `src/generated/ai-catalog.json`.
- **Derived skill names are transliterated and cut to 64 characters** (every config). Letters such as `ß`, `æ` and `ø` are now written as `ss`, `ae` and `o` instead of becoming hyphens (`Grüße Welt` was `gru-e-welt`, now `grusse-welt`). The SKILL.md frontmatter, the skills index and its digest change for such names.
- **Advertisements follow the features.** With `[features].manifest = false` the Link header and the `<link>` tag drop `rel="webmcp"`, and llms.txt, agents.md and SKILL.md drop their manifest line. With `webmcp_landing = false`, llms.txt, agents.md, SKILL.md and the manifest's `links.landing` stop naming the landing page. The Link header is left out when nothing is left to advertise, and it is now added to proxied responses with `[features].inject_html = false` too (before, it was not).
- **The landing page is called a pairing page only when the widget is on.** llms.txt says "WebMCP page" instead of "Pairing page", agents.md has a "WebMCP page" bullet instead of the "Desktop MCP clients ... pair at" bullet and no widget note, and SKILL.md says "The tools are also listed at <landing>" (with a custom landing template, "The WebMCP page is <landing>") instead of "Desktop MCP clients can pair at", unless `fallback_widget = true` and the build has a usable widget pin. The SKILL.md bytes and its digest in the skills index change for a config without the widget.
- **agents.md and SKILL.md say only what the config does.** They name the runtime as `document.modelContext` (Chrome 146 to 149: the deprecated `navigator.modelContext`) and no longer say "Chrome with WebMCP flag enabled". Where the tools register follows the config: with `[features].inject_html` on, on the pages that load the cf-webmcp script; with it off, on the landing page when it uses the default template; with a custom landing template, or with the landing off as well, nothing is said. Form tools are listed only while `inject_html` is on (the Worker stamps no form otherwise), and so are they in the ARD entry's `capabilities`; while they exist the exec, manifest, landing and pairing lines say "the tools that are not forms". agents.md promises `Retry-After` only for the Worker's own rate limit, and links `/_webmcp/health` only when it answers without a token. The SKILL.md digest in the skills index changes.
- **The API catalog is not served while the manifest is off.** Its one entry is the link to the manifest, and RFC 9727 section 4.1 requires an API catalog to link to API endpoints. With `[features].manifest = false` the route is not claimed in any mode (synthesize, replace or merge; the path stays with origin), and the Link header, the `<link rel="api-catalog">` tag, the llms.txt line, the manifest's `links.api_catalog` and the preflight probe drop out; the build warns. Set `[features].api_catalog = false` to say so.
- **The API catalog's `Content-Type` carries the RFC 9727 profile.** It is `application/linkset+json; profile="https://www.rfc-editor.org/info/rfc9727"` (RFC 9727 section 4.2); it was `application/linkset+json`. A client that matched the bare media type string needs to compare the type only.
- **The skills index is served only when it can list a real digest.** `index.json` needs `[features].agent_skills` on in `synthesize` or `replace` mode. With `agent_skills` off, in `merge` or in `passthrough` mode it is no longer served: before, it was a 200 that listed a SKILL.md whose path went to origin (agent_skills off), or a 404 with an explanatory body from the Worker (merge and passthrough); now the path stays with origin, the manifest has no `links.agent_skills_index`, and the build warns. A skill name is no longer required for an index that is not served.
- **`passthrough` is honoured for llms.txt, robots.txt and agents.md.** With `mode = "passthrough"` the Worker no longer claims the path (nor, for agents.md, its alias redirects): the request goes to origin like any other, with only the Link header added.
- **llms.txt and robots.txt never carry `X-Robots-Tag` at their apex paths.** Whatever the two routes answer (a merged file, a relayed origin answer, a 502 or a 504), any `X-Robots-Tag` is removed, origin's included. A path moved under the namespace or `/.well-known/` carries `noindex` like every route there.
- **Merge routes read at most 1 MiB of origin's file.** llms.txt, robots.txt, agents.md, the API catalog and the agent skill (merge mode) now relay a larger file as it came, with the route's `X-Robots-Tag` rule, instead of merging it; a body that fails mid-read is answered with what the route serves when origin has no file, cached for 60 seconds, instead of the platform's error page. The ARD manifest does the same (see above). robots.txt does not: its block alone would drop origin's `Disallow` rules, so a failed read answers `503` with `Retry-After: 60` and `Cache-Control: no-store`, which crawlers treat as a temporary error. See [Merge routes and the 1 MiB cap](deployment.md#merge-routes-and-the-1-mib-cap).
- **Merge routes time out and fail cleanly.** A merge route waits at most 10 seconds for origin's response headers, then answers `504` (the ARD manifest serves its generated document instead). A failed origin fetch answers `502`; in v0.5.1 it was an uncaught Worker error.

#### Routing and HTTP

- **`/mcp` answers page requests only.** The landing page answers GET and HEAD requests unless their `Accept` contains `text/event-stream`; every other method (an MCP client's `POST` or `DELETE`), and a GET or HEAD that asks for an event stream, go to origin, so an MCP server at origin on the same path stays reachable (Cloudflare WebMCP Labs sends its MCP requests to `/mcp`). Before, every request to the path got the landing page. The landing page and its 308 (for a landing path that ends in `/`) send `Vary: Accept`, and the 308 is `Cache-Control: no-store`. See [`docs/scope.md`](scope.md).
- **Redirects under `/.well-known/` or the namespace carry `noindex`.** An `[agents_md].aliases` entry placed there (`/.well-known/AGENTS.md`, say), and the slash-less form of a `[webmcp_landing].path` placed there (`/.well-known/mcp` for `/.well-known/mcp/`), now answer their redirect with `X-Robots-Tag: noindex`; before, they sent none. The redirects of the manifest, ARD manifest and agent skill aliases already did. At the apex, as by default, nothing changes.
- **Unknown paths under the namespace answer 404.** A path under `[paths].namespace` that is not a cf-webmcp route (a typo, an exec path with an invalid tool name) gets `404` with `Cache-Control: no-store` and `X-Robots-Tag: noindex`, and is never proxied to origin. So does a `bootstrap.<x>.js` or `widget.<x>.js` that is not the current one, such as a URL from an earlier deploy.
- **Origin redirects on the Worker's own requests are checked hop by hop.** Executors and merge routes no longer let the runtime follow redirects: each `Location` is requested only when its origin is in `allowed_origins`, for at most 5 hops, so the deploy-token headers never leave the list. A merge route relays a redirect to an origin outside the list to the client as it came, with `Cache-Control: no-store`, instead of following it (the ARD manifest answers its generated document instead); an executor refuses it (`invalid_input`). More than 5 redirects answers `502` on a merge route and `internal` on an executor. v0.5.1 let the runtime follow redirects with the deploy-token headers attached and checked only the final URL: an off-list one then answered `502` on a merge route and `invalid_input` on an executor. See [Origin and allowed_origins safety](deployment.md#origin-and-allowed_origins-safety).
- **Rewritten HTML gets suffixed ETags and no `Last-Modified`.** A page the Worker injects into carries origin's `ETag` with `-<INJECTION_HASH>` inside the quotes, so a deploy that changes the injected output reaches pages a browser revalidates. After deploying v0.6.0, a page load (a request whose `Accept` names `text/html`) that revalidates a copy cached before the upgrade refetches it once, in full. A request without `text/html` in its `Accept` (a script's `fetch()` with `*/*`, say) that revalidates such a copy can still get a `304` from origin and keep the old copy, which points at a bootstrap URL that now answers 404, until origin's page changes or the copy leaves the cache. See [Caching](deployment.md#caching-and-the-deploycache-bust-cycle).
- **Revalidating a page load.** On a path the Worker rewrites, a page load whose copy does not carry the current suffix is answered in full, never with a `304`, also when origin's answer turns out not to be rewritten (a non-UTF-8 page, say). `If-Match` loses the current suffix on the way to origin, so a conditional `PUT` or `DELETE` with a tag from a rewritten page meets origin's own tag.
- **The manifest, the landing page and the ARD manifest send body ETags.** Their `ETag` is the hash of their own body instead of `CONFIG_HASH`; the ARD manifest gets an `ETag` for the first time.
- **HTML injection fails open.** If building the HTML rewriter throws, the Worker logs the error and serves origin's page unchanged; a `[[forms]]` selector that HTMLRewriter rejects at request time skips only that form or param. In v0.5.1 such an error was not caught and the request failed (with `inject_html` on; with it off there was no rewriter).
- **WebSocket upgrades pass through.** A `101` from origin is returned as it came; in v0.5.1, with `inject_html` and `link_header` on, adding the Link header to it threw.
- **The rate limiter keys IPv6 clients by /64 and ignores `X-Forwarded-For`.** Addresses in one /64 share a bucket. The key comes from `CF-Connecting-IP`. When that holds a Class E address (240.0.0.0/4), which is what Pseudo IPv4 set to overwrite headers puts there, the real address in `CF-Connecting-IPv6` is used instead; next to any other address `CF-Connecting-IPv6` is ignored, because a client can send one of its own. Requests without `CF-Connecting-IP`, or with a value that is not an IP address, share one bucket. A full bucket table evicts its 1024 least recently used entries instead of refusing new clients.

#### Tool calls

- **Only declared properties reach an executor, and the exec cache is keyed on them.** The exec route passes on the properties of the request that the tool's `input_schema` declares; the executor, its URL, a POST body and the cache key are all made of those. The cache key is the cf-webmcp version, `CONFIG_HASH`, the tool name and the canonical JSON (sorted keys) of that input, so a request that differs only in key order, whitespace or undeclared keys is one cache entry, and an upgrade or a config change starts a fresh cache.
- **Exec CORS is worked out per request.** In v0.5.1 an answer from a tool run carried CORS for a listed origin, and a cache hit replayed the headers of the caller that filled the cache. Now the cache stores no CORS headers and every answer works them out for its own request, and the route's own answers (405, 404, 400, 413, 429) carry CORS for a listed origin too. While `[cors].allowed_origins` is set, every exec answer sends `Vary: Origin`, except the `OPTIONS` preflight, which sends it only when it answers a listed origin. Answers for a listed origin carry `Access-Control-Expose-Headers: x-webmcp-cache`, so a script there can read `X-Webmcp-Cache` (`HIT`, `MISS` or, for an uncached tool, `BYPASS`).
- **`http_json` POST tools send a body, are not cached by default, and default to `consequentialHint`.** `method = "POST"` now sends the declared properties of the validated tool input to origin as the JSON body (`content-type: application/json`; `{}` when the tool declares none); before, it sent a POST with no body. A POST tool is cached only when `[tools.cache]` sets `s_maxage` greater than 0 (`max_age`, `swr` or `sie` alone do not turn caching on, and the build warns about such a table); otherwise it answers `Cache-Control: no-store`. Its `readOnlyHint` defaults to `false` and `consequentialHint` to `true`; set `[tools.annotations]` to say otherwise. GET tools still send no body and keep their caching and hints; the response limits below apply to both methods.
- **Executors read bounded responses, within one deadline.** `http_json` and `rss_feed` read at most 2 MiB of origin's response and `sitemap_filter` at most 5 MiB; a larger body answers `response_too_large`. A sitemap over 5 MiB that worked in v0.5.1 now fails. The 8 second deadline now covers the body reads too, not only the wait for origin's headers. An executor that throws answers `internal` instead of failing the request.
- **Executor redirects follow the fetch method rules.** A `307` or `308` repeats a POST with its body; a `301`, `302` or `303` turns the next request into a GET without a body.
- **The exec route reads the request body as a stream.** A body over 64 KiB is refused with `413` and the message `request body too large` (it was `body exceeds 65536 bytes`), also without a `Content-Length`, before more than that is buffered. A body the client stops sending answers `400` (`could not read request body`).
- **Errors about the origin request no longer echo hosts, URLs or runtime text.** A refused redirect, a resolved tool URL that does not parse (`resolved URL is malformed`) or whose origin is not in `allowed_origins` (`resolved origin is not in allowed_origins`), and an origin fetch that fails (`origin request failed`; it was the runtime's own message, which can name a host or an address) answer fixed messages. So do a `sitemap_url` or `feed_url` the Worker cannot use. An `http_json` answer that is not JSON reports `origin did not return valid JSON` without the parser's message. The detail goes to the Worker log (see [What the Worker logs](privacy.md#what-the-worker-logs)).
- **The deploy token is taken out of tool output.** With `CF_WEBMCP_DEPLOY_TOKEN` set, every occurrence of the token's value in an executor's answer (`http_get`, `http_json`, `dom_extract`, `rss_feed` and `sitemap_filter`, an error message included) is replaced with `[redacted]`: as written and as JSON writes it inside a string, checked after any JSON parse. An origin endpoint that echoes request headers can no longer hand the token to a caller. The merge routes do the same and drop any response header that holds it; their answers then carry no `Content-Length` (see [Merge routes and the 1 MiB cap](deployment.md#merge-routes-and-the-1-mib-cap)). Other encodings of the token are not recognised (see [`docs/security.md`](security.md#defence-in-depth-in-cf-webmcp-itself)).
- **A path placeholder in a `url_template` cannot climb out of its path.** A security fix. With `url_template = "https://example.com/api/{{id}}"`, `id = "../../admin"` used to be resolved by the URL parser to `https://example.com/admin`, requested with the deploy-token headers. Now a value in a path position that holds a `.` or `..` segment (raw, percent-encoded in any case or mix, doubly encoded, or split by `\`) is refused as `invalid_input`, and the resolved pathname must start with the static path in front of the first placeholder (`/api/` here; `/` for a root template such as `https://example.com{{path}}`, which still takes any normal path). `v1.2`, `file.json` and `..foo` are unaffected. A `%2F` a caller writes stays literal text (`%252F` on the wire). See [`docs/limitations.md`](limitations.md#a-path-placeholder-cannot-climb-out-of-its-path).
- **An array property without `items` holds scalars only.** Elements must be strings, numbers or booleans, or arrays of those (at most 8 levels); an object or `null` is refused. The schema subset has no object type, so such an element was never a declared shape. Typed `items` are unchanged.
- **Input validation and extraction fixes.** `enum` is now enforced on integer, number and boolean properties too (see Enums under [Config that changes meaning or fails to build](#config-that-changes-meaning-or-fails-to-build)). A `required` or unknown-property check no longer counts names every object has (`constructor`, `__proto__`, `toString`). `dom_extract` keeps the text after a nested element the selector also matches (`<article>` inside `<main>`) and accepts void tags such as `img`, `br` and `input` in `strip`.

#### Bootstrap, landing page and widget

- **The bootstrap is addressed by its content alone.** It was named after the config hash (`bootstrap.<8 hex CONFIG_HASH>.js`) and moved with every TOML edit; it is now `bootstrap.<16 hex>.js`, the hash of its own bytes, so the URL and its SRI hash move only when `[[tools]]`, `[paths].namespace` or the generator changes. Both change once with this upgrade. The injected `<script src>` names the origin of the request (`www`, `workers.dev` and preview hosts load the script from themselves); it was the configured site URL. Discovery documents keep absolute URLs on the site URL.
- **The bootstrap registers more carefully.** It skips a tool name that `getTools()` already lists (waiting at most 1500 ms for the answer), keeps a page-wide record of the names it registered so a second run on the same page adds nothing, passes an abort signal per tool to `registerTool` (from Chrome 153, aborting it unregisters the tool), and calls the exec endpoints on the page's own origin (root-relative under an opaque origin) instead of the configured site URL. When the browser has WebMCP and the Cloudflare WebMCP Labs bridge script is in the page, it logs a console note.
- **A page without `</body>` gets the bootstrap at the end of the document.** v0.5.1 put the script only before `</body>`. A bare fragment (no doctype, `<html>`, `<head>` or `<body>` tag) is still left alone.
- **The landing page loads the bootstrap.** The default template's `{{bootstrap_block}}` (a root-relative `src`, with SRI while `[features].subresource_integrity` is on) registers the site's tools on the landing page itself, so "Connected" is true of that page and its diagnostic lists the names `getTools()` returns. A custom template without the placeholder loads no bootstrap, as before.
- **The default landing page's copy and diagnostic changed.** Next to the testing flag it now names the Chrome origin trial (from Chrome 149) and Kitesurf, and its diagnostic names the host it selected and lists the names `getTools()` returns.
- **The fallback widget works.** Before, the landing page loaded the widget script but never started it, and the pairing steps ran the bridge at `@latest`. Now `{{widget_block}}` starts the widget and registers the site's tools with it, and every pairing command names the bridge release of the pinned widget. The visitor starts the bridge with `--foreground` in a terminal, adds the client entry by hand (the page shows the Claude Desktop entry, the Cursor file and the Claude Code command) and pastes a pairing token. The widget disconnects after 30 minutes without mouse movement, clicks, key presses or scrolling on the page. The bridge has limits cf-webmcp cannot remove: see [Known limits of the desktop bridge](deployment.md#known-limits-of-the-desktop-bridge).

#### Build and preflight

- **Preflight is strict about its arguments, and reports oversize files.** An unknown flag, a stray argument, `--origin` or `--config` without a value and a flag given twice (`--force --force` too) are usage errors (exit code 2); unknown flags were ignored before. `--config <path>` with a space is now accepted, as is the new `--origin` (see [Additions](#additions)). A merge-path file over 1 MiB is reported as "too large to merge, relayed unchanged" (a warning) instead of "merge"; an ARD document at a merge path, which v0.5.1 preflight did not probe, is judged the same way. The API catalog in `merge` mode, its default, is a merge row (a valid linkset at origin was a COLLISION before), and content types are judged as the Worker judges them.
- **Preflight can now exit 1 where it passed before.** A row is a merge only in a mode where the Worker fetches origin's file. In `synthesize` and `replace` mode a file at origin for llms.txt, agents.md or the agent skill (which defaults to `synthesize`) is a collision; v0.5.1 reported these as merges. A `200` at the ARD manifest path or one of its aliases in `synthesize` mode is a collision too, and so is one at the slash-less form of a landing path that ends in `/`.
- **Preflight sends the deploy token only to a listed origin.** A `base_url` whose origin is not in `[origin].allowed_origins` now stops preflight with the build's own error before any request (exit code 2); before, preflight probed it with the token. The new `--origin` host (see [Additions](#additions)) gets them only when `allowed_origins` lists it; any other is probed without them. If your origin's WAF needs them on that host, add it to `allowed_origins`. Preflight also warns when the token would go over plain `http` to a host other than `localhost`.
- **Preflight reads `inherits`** the way the build does, so it checks the same merged config and stamps its result with the build's `CONFIG_HASH`.
- **The build reads `vendor/webmcp/current.json` even with the widget off,** and fails when it is not valid JSON. A pin without valid `served_sha256` and `served_sri` (one written by an older `update-widget`) builds with no widget and, with the widget on, a warning.
- **`update-widget` and `upload-widget`.** `update-widget` accepts only a release tag `vX.Y.Z` as `--version` and by default downloads `src/webmcp.js` at that tag. `upload-widget` passes `--remote` to wrangler, and `-- --local` writes to the local state of `wrangler.dev.toml` (see [Pin the fallback widget](deployment.md#pin-the-fallback-widget-optional)). With the widget on, the build warns when the license preamble no longer matches the pin's `preamble_sha256`; `upload-widget` then refuses to upload until the pin is regenerated. `upload-widget` also refuses, before it runs wrangler, a bucket name that breaks R2's naming rule and a wrangler config path or temporary directory with a character the shell would interpret (`$`, a backtick, `%`, a quote, `;`, `&`, `|`, `<`, `>`, a line break): it runs wrangler through a shell, where quoting does not stop `$(...)` or `%VAR%`.
- **The build warns about a `url_template` rooted at the origin.** When the first placeholder of a `dom_extract`, `http_json` or `http_get` template comes straight after the origin (`https://example.com{{path}}`), a caller can have any path on the origin requested, with the deploy-token headers. The build names the tool and suggests a fixed path prefix (`https://example.com/docs/{{path}}`); it still builds. A placeholder that only takes values the publisher fixed (a `map:` operator, or an `enum` on its input property) gets no warning. The `get_page` tool of the default template (and of the example site) is such a tool, so a TOML built from it gets the warning; keep the tool if it should read any page, or narrow it.
- **The build warns about an `[origin].allowed_origins` entry with a path.** Only the origin of an entry was ever compared, so `https://example.com/blog` allowed all of `https://example.com`. The build now says so for every entry with a path, query or fragment, naming the entry and the origin it allows; it still builds.
- **The build warns about `[origin].forward_cookies = true`.** The key does nothing: executors and the Worker's other origin fetches never send the visitor's cookies, and the proxy relays requests as the visitor sent them. `[dev].origin` does nothing either. Remove both.

### Additions

- **`[origin_trial].tokens`** for Chrome's WebMCP origin trial (from Chrome 149). The Worker sends each token as an `Origin-Trial` header on proxied HTML `200` responses, on `304`s that answer a page load, and on the landing page; in route-only mode only the landing page carries them, so have origin send the header on your other pages. The build checks each token (see above) and warns about one that expires within 30 days, and `/_webmcp/health` lists each token's feature, expiry and whether it has expired, never the token. See [`docs/browser-support.md`](browser-support.md#the-chrome-origin-trial).
- **`[tools.annotations].consequential_hint`**, Chrome's `consequentialHint` (a call the user may not be able to take back). Every tool now carries it: `false` by default, `true` for an `http_json` POST tool.
- **`[ai_catalog].skill_type`**: the ARD skill entry's `type`, `application/ai-skill+md` by default, or `text/markdown; profile="urn:air:agent-skills"` or `application/agent-skills+md`.
- **`{{bootstrap_block}}`**, a landing-template placeholder for the bootstrap `<script>` (a root-relative `src`, with SRI while `[features].subresource_integrity` is on). Include it once; a template that contains it more than once fails the build.
- **`npm run preflight -- --origin=<url>`** sends the probes (and the deploy token, when `[origin].allowed_origins` lists that origin) to another origin, such as a direct origin hostname, with the config untouched, so preflight still says something about origin once the hostname is routed through the Worker. See [Preflight](deployment.md#preflight).
- **Preflight looks for an MCP server at the landing path.** It POSTs a JSON-RPC `initialize` there and warns when origin answers `200` with JSON or an event stream.

## v0.5.0: ARD ai-catalog (opt-in)

v0.5.0 adds an [Agentic Resource Discovery (ARD)](https://github.com/ards-project/ard-spec) publisher catalog at `/.well-known/ai-catalog.json`. When enabled, cf-webmcp synthesizes a catalog with one entry derived from the site's Agent Skill and advertises it via four surfaces: a `robots.txt` Agentmap directive, `rel="ai-catalog"` in the HTTP Link header and as an HTML link tag, and a line in llms.txt.

**This feature is OFF by default.** ARD is a v0.9 draft; the media types (`application/ai-catalog+json`, `application/ai-skill+md`) are not yet IANA-registered. Enable only after evaluating spec stability.

To enable:

```toml
[features]
ai_catalog = true

[ai_catalog]
mode = "synthesize"   # or "merge" if your origin already publishes an ai-catalog.json
```

Available modes: `synthesize` (default, generate from config only), `merge` (splice into origin's catalog), `passthrough` (route not registered). See [`docs/ai-catalog.md`](ai-catalog.md) for all config fields.

No breaking changes. Existing TOMLs work unchanged - the new fields all have defaults and the feature gate is `false`.

## v0.4.1: duplicate WebMCP tool-name crash hardening

Registering the same WebMCP tool name twice on one page kills the Chrome renderer (`bad_message` 345, `RFHI_WEBMCP_REGISTER_DUPLICATE_TOOL_NAME`) - a browser-side Mojo IPC validation kill that no `try/catch` can trap. cf-webmcp emits two registration surfaces on a page (the bootstrap's `registerTool` calls and any `<form toolname>` it stamps from a `[[forms]]` rule), so a name shared across `[[tools]]` and `[[forms]]` would crash. v0.4.1 closes this on both ends:

- **Build-time guard.** The build now fails if any name is duplicated within `[[tools]]`, duplicated within `[[forms]]`, or shared between `[[tools]]` and `[[forms]]`. Rename one side to fix. (No action needed unless your config already had such a collision, in which case the build will now tell you.)
- **Runtime de-dupe.** The injected bootstrap scans `[toolname]` elements on the page and skips registering any tool whose name is already declared declaratively - covering names you hand-stamped in origin HTML, which the build cannot see.
- **Host detection order.** The bootstrap now probes `document.modelContext` (current, Chrome 150+) before `navigator.modelContext` (the deprecated 146-149 binding, whose accessor logs a console deprecation warning). No behaviour change on browsers that expose only one.

## v0.4.0: manifest path is extensionless by default

As of v0.4.0 the default WebMCP manifest path is **`/.well-known/webmcp`** (extensionless), matching the convention of IANA-registered well-known suffixes (`api-catalog`, `openid-configuration`). The legacy `/.well-known/webmcp.json` is kept as a **301 redirect alias** by default, so older links and any cached `rel="webmcp"` references keep working.

- No action is required: rebuilding moves the canonical manifest to `/.well-known/webmcp`, advertises that path in the `Link` header / `<link rel="webmcp">` / llms.txt / agents.md, and 301s the `.json` path to it.
- To keep `.json` as the canonical path instead, set `[manifest].path = "/.well-known/webmcp.json"` and `[manifest].aliases = ["/.well-known/webmcp"]` (or `[]` to disable the redirect).
- The injected bootstrap also gained feature detection and a corrected return shape:
  - It registers tools on whichever host object exposes `registerTool` - `navigator.modelContext` (current Chrome Canary) or `document.modelContext` (the Apr 2026 WebMCP draft) - and no-ops when neither is present.
  - Each tool's `execute` now returns the WebMCP/MCP tool-result shape `{ content: [{ type: "text", text }], isError }` instead of cf-webmcp's raw `{ ok, data }` envelope. The full executor envelope is carried as the `text` payload (so the agent keeps structured success/error), and `isError` mirrors `ok: false`. The `POST /_webmcp/exec/<tool>` endpoint itself is unchanged and still returns the envelope; only the in-page registered tool adapts it to the runtime's expected shape.

## Schema version

Every `webmcp.toml` declares `schema_version = 1` at the top. The build script refuses unknown versions. `schema_version` stays 1 until cf-webmcp 1.0. Before 1.0, a minor release may still need TOML changes; its notes list them under "Config that changes meaning or fails to build" (v0.6.0 is such a release). From 1.0 on, a breaking change to the TOML format bumps this number and needs a manual migration step.

There are no silent migrations.

## Tool name immutability

Tool names are permanent once they have been advertised in a deployed manifest. If an agent has cached the manifest and the publisher renames `search_products` to `find_products`, the agent's cached tool reference 404s.

Recommended workflow:

- To add capability: add a new tool with a new name.
- To remove capability: delete the tool from the TOML on deploy. Old agents see `not_found` on that tool name. Acceptable.
- To change behaviour of an existing tool: change the executor, leave the name and description stable.

## Config hash

Every build computes `CONFIG_HASH`: the first 8 hex chars of the sha256 of the validated config, with `inherits` resolved and every default filled in. It changes when a value in the validated config changes (in the TOML or in the TOML it inherits), or when an upgrade adds or changes a default. The hash:

- Appears in `/_webmcp/health` and in the manifest's `config_hash`, so the operator can confirm which config is live.
- Keys the exec cache together with the cf-webmcp version, so neither a config change nor an upgrade answers from results of the previous deploy.

It is not an `ETag`. The manifest, the landing page and the ARD manifest carry the sha256 of their own body as `ETag`, which also moves when a cf-webmcp upgrade or a widget pin change alters the body while the TOML stays the same. llms.txt and robots.txt carry no `ETag` of their own; when they relay origin's answer as it came (an error, a body they do not merge, or a file over the 1 MiB merge cap), origin's headers go with it, its `ETag` included.

The config hash does **not** name the served scripts. Both are content-addressed, so a URL changes exactly when the bytes behind it change:

- `bootstrap.<hash>.js`: `<hash>` is the first 16 hex chars of the sha256 of the generated bootstrap itself. A change to `[[tools]]` (a name, title, description, input schema or annotations, or the executor type when that changes the tool's default annotations) or to `[paths].namespace` moves it, and so does a cf-webmcp upgrade that generates a different bootstrap from the same TOML; other TOML edits do not. The `integrity` hash on the injected `<script>` always matches the file at that URL.
- `widget.<hash>.js`: `<hash>` is the first 16 hex chars of the sha256 of the object in R2 (license preamble plus the pinned widget), recorded in `vendor/webmcp/current.json`. Editing your TOML does not move it; changing the widget pin does.

## Updating the fallback widget

```bash
npm run update-widget -- --version=vX.Y.Z --sha256=<hex>
npm run upload-widget      # BEFORE deploy
npm run deploy
```

The sha256 is verified during download. If the upstream release has been replaced or modified, the pin fails. Always pull the upstream LICENSE file alongside the JS.

`update-widget` also records `served_sha256`, `served_sri` and `preamble_sha256` in `vendor/webmcp/current.json`. Commit that file with the pin change. `upload-widget` re-checks the vendored file against those values before it uploads anything, and the build reads only `current.json`.

Upload before deploy: the new Worker advertises the new widget URL on the landing page and answers 503 for it until the object exists. `/_webmcp/health` reports `widget_asset_present` so you can confirm. The object for the previous pin (and any old `widget.<8-hex>.js` object named after a config hash by v0.5.x and earlier) is no longer referenced and can be deleted from the bucket.

## Updating the Worker itself

`cf-webmcp` follows semver:

- Patch (`0.1.0` → `0.1.1`): bug fixes, internal changes. Safe to pull and redeploy without TOML changes. If the release changes the generated bootstrap, the redeploy moves the bootstrap URL and its SRI hash automatically; there is nothing to configure, but a CSP that allowlists the bootstrap by hash needs the new `BOOTSTRAP_SRI` (see [`docs/deployment.md`](deployment.md#subresource-integrity-sri-on-the-injected-bootstrap)). If it changes the widget pin or the license preamble, run `npm run update-widget` and `npm run upload-widget` before deploying.
- Minor (`0.1.0` → `0.2.0`): new features, new optional TOML fields. May add new executor types. While cf-webmcp is 0.x, a minor release may also need TOML changes: the release notes list them under "Config that changes meaning or fails to build".
- Major (`0.x` → `1.0`): breaking changes. `schema_version` bumps. Manual TOML migration documented in the release notes.

Subscribe to releases on GitHub to be notified.

## Migration from v0 to a hypothetical v2

When v2 lands, the build script reads `schema_version` and either:

- Migrates in place automatically if the change is backwards-compatible and we ship a migration. The TOML is rewritten on disk with the new version stamp.
- Or fails with a clear message telling the publisher exactly what to change. Migration instructions live in `docs/migrations/v1-to-v2.md`.

No version of `cf-webmcp` will silently accept a TOML with the wrong `schema_version`.
